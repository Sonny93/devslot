# Decisions

One line per decision: date, decision, reason.

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-11-10 | `ds` writes `COMPOSE_FILE` into the `.env` block only when no compose file with a Docker default name (`compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`) exists at the checkout root. It always passes `-f <dev compose>` (plus the project's `compose.override.*` if present) to the compose commands it runs itself, and sets `COMPOSE_FILE` in the environment of processes it launches (`ds run`, the `run` key). | Verified with `docker compose config` on the Adonis template: with `COMPOSE_FILE=dev.compose.yml` in `.env`, the bare `docker compose up` of the `just prod` recipe silently starts the dev compose (Postgres only, no app), and the template's dev recipes all pass `-f`, so the line brought nothing. |
| 2026-11-10 | Known limitation: dev and local prod share the compose project. `COMPOSE_PROJECT_NAME` in the block also applies to the prod compose of a registered checkout, so local prod runs on the dev database volume of that checkout. Workaround: `-p <name>` in the prod recipe. The `env_file` rule is necessary for `just prod` to work, not sufficient. | Accepted because the user never runs both at once and devslot stays a dev tool; verified that `-p` takes precedence over `COMPOSE_PROJECT_NAME`. |
| 2026-11-10 | Open point for v2: the sharing design (override loaded through `COMPOSE_FILE`, "`DB_PORT` and `COMPOSE_FILE` always together") is not loaded by recipes that pass `-f`, including `ds run -- just dev`. Recorded as unresolved, with no solution proposed. | Verified that `-f` on the command line takes precedence over `COMPOSE_FILE`. |
| 2026-11-10 | The `env_file` check warns for every managed port variable a service receives through `env_file` without pinning it in `environment:`, `VITE_HMR_PORT` included. | A host-side port in a container breaks it whichever variable carries it. |
| 2026-11-10 | Vite detection walks recursively from the checkout root honoring `.gitignore` (Rust `ignore` crate), skipping `node_modules` and hidden directories, looking for a `package.json` with `vite` and for `vite.config.*`. It warns when more than one Vite config is found. | The walker is the one ripgrep uses, and a single `VITE_HMR_PORT` would be shared by several Vite configs. |
| 2026-11-10 | `ds doctor` exit codes: 0 when there is no error (warnings allowed), 1 when at least one error is found, 2 when the tool itself fails or on usage error. | Same convention as grep and diff, so scripts can tell a finding from a failure. |
| 2026-11-10 | `ds doctor` scans the 10 detection names plus `*.compose.y(a)ml`, `compose.*.y(a)ml` and `docker-compose.*.y(a)ml` at the root. | Covers the compose variants a project can name beyond the detection list. |
| 2026-11-10 | The bind mount check warns when the resolved source path is outside the checkout root. | `docker compose config` outputs absolute paths, so "written as absolute" cannot be detected. |
| 2026-11-10 | The hardcoded port check inside a value warns only when a local host (`localhost`, `127.0.0.1`, `0.0.0.0`, `[::1]`) is followed by `:<default port of a managed variable>` not followed by a digit (example `DATABASE_URL=postgres://u:p@localhost:5432/app`). | No false positives on external hosts (SMTP, remote DB). |
| 2026-11-10 | CLI messages, README and all docs (spec and decisions included) are in English. The French spec stays in git history. | One language for every reader and contributor. |
| 2026-11-10 | `toml_edit` instead of `toml` for the registry and config. | Hand-written comments survive rewrites. |
| 2026-11-10 | Automatic registration through a hook: the Claude Code plugin ships a `PreToolUse` hook (matcher `Bash`) that runs `ds ensure` on the hook input's `cwd` before every Bash command of the agent. `ds ensure` is idempotent: for a registered checkout it reads the registry only (no Docker call, must be fast); for an unregistered checkout with a dev compose it registers it, allocates its slot, creates `.env` if missing and writes the block; for a repo without a compose it exits immediately. It never starts services. The hook never blocks the agent's command: on failure it reports the problem to the agent and lets the command run. This replaces revision 3's "no PreToolUse hook in v1" and "the SessionStart hook registers nothing"; the optional SessionStart hook that adds `ds info` to the context may stay. | Deterministic and turnkey, and it covers worktrees created or entered mid-session (`EnterWorktree` does not fire `SessionStart`), unlike a skill instruction. |
| 2026-11-10 | Scope of automatic registration: every repo by default. The global config gets an `[auto]` section with `include` and `exclude` lists of path globs; an empty `include` means everywhere; `exclude` wins. | Works out of the box and stays restrictable. |
| 2026-11-10 | Missing `.env`: instead of stopping, `ds` creates it by copying the main checkout's `.env` (the main worktree of the repo) with its devslot block stripped, otherwise `.env.example`; it stops with an error only when neither exists. Each creation is announced with the file path. | A new worktree never has `.env` (git ignores it), and daily use must be turnkey. |
| 2026-11-10 | `ds up`, `ds run` and `ds ensure` refuse to write the block into a `.env` that git does not ignore. This turns the existing warning into an error for writing, and `ds doctor` reports it as an error. | The block would end up in a commit. |
| 2026-11-10 | Duplicate keys in `.env`: the block stays at the end of the file, between markers, and original lines such as `PORT=3333` are left untouched. No commenting or restoring of original lines; `ds rm` just removes the block. | Verified: Compose v5.7.0, dotenv 17.4.2 and `@adonisjs/env` 7.1.0 `EnvParser` all keep the last value of a duplicated key. |
| 2026-11-10 | Prototype checklist: "the sentinel method finds each port variable with its service and container port" is ticked; "none of your composes has `container_name`..." is answered: false. | Sentinel method verified on Compose v5.7.0 with the template (`DB_PORT=9001` comes out as published 9001, container port 5432); my-links has `container_name` in `compose.yml` and `compose.image.yml`. |
| 2026-11-10 | Existing tools evaluated, not adopted: worktree-compose (npm, MIT, 1.0.0) and Docktree (Go). Decision: build devslot. Worth reusing from worktree-compose: copying `.env` from the main checkout. | Read from source: worktree-compose computes ports per repository without a machine-wide registry (two projects collide), does not handle an app running outside Docker and only uses the default-named compose; Docktree has no license file and never writes `.env`. |
| 2026-11-10 | `ds rm` marks the checkout as opted out in the registry: `ds ensure` (the hook) skips it, and only an explicit `ds up` or `ds run` registers it again and clears the mark. `ds prune` forgets opted-out checkouts whose folder no longer exists. | Without it, the automatic hook would register a checkout again on the next agent command, so the main checkout could never go back to the default ports. |
| 2026-11-10 | Sentinel candidates: a compose variable gets a sentinel only when its usual value (the compose default, otherwise its value in `.env` with the devslot block stripped, otherwise `.env.example`) is a number or empty. `[ports] ignore` variables still get one and are filtered out afterwards. A variable with a non-numeric value (`DB_USER=root`, `BIND_IP=127.0.0.1`, `HC=30s`) gets none. Port ranges are not managed and give a warning. If Compose still rejects the probe, `ds doctor` reports it as an error. | A sentinel on every variable makes Compose reject typed fields (`invalid IP address: 61002`, `missing unit in duration`). A YAML parser was considered and rejected: it would have to reimplement `include`, `extends`, multiple files, overrides, anchors, every port syntax and interpolation. |
| 2026-11-10 | Compose probes run with a cleared environment (only `PATH`, `HOME`, the `DOCKER_*` variables and the sentinels), `--env-file /dev/null`, `-p devslot-probe`, `--profile '*'` and `--no-env-resolution`, with a timeout. Test fixtures are written from synthetic compose files and fake `.env` files, never recorded from a real project. | Verified on Compose v5.7.0: without this, interpolation copies `.env` values, passwords included, into the JSON (`POSTGRES_PASSWORD`). With `--env-file /dev/null` they come out empty, and `env_file` paths stay visible. `--profile '*'` includes profiled services. |
| 2026-11-10 | `ds doctor`: a scanned compose file that `docker compose config` rejects on its own gives a "skipped, cannot be read on its own" warning; for the selected dev compose it is an error. `compose.override.*` is never scanned on its own: it is merged into the dev compose and into the default-named compose, as a bare `docker compose` and `ds` do. Without any compose file, doctor prints an info line and the other checks still run (exit 0 if no error). | Override files and fragments fail `config` alone (`service has neither an image nor a build context`), and a sound project must not fail doctor. |
| 2026-11-10 | Default value of a managed compose variable: the compose default (`${DB_PORT:-5432}`), otherwise its value in `.env` (block stripped), otherwise `.env.example`, otherwise none. No warning when `:-default` is missing. | The template and my-links write `${DB_PORT}` without a default, yet the default is needed for display and for the local host value check. |
| 2026-11-10 | A `.env` that cannot be parsed is an error finding of `ds doctor` that gives the line number only, never the line. A malformed devslot block (start marker without end marker, or more than one block) is also an error finding. | The line can hold credentials. A malformed block must stop the phase 3 writer instead of letting it delete user lines. |
| 2026-11-10 | Vite warning also when a `package.json` lists `vite` and no `vite.config.*` exists. | Vite then keeps its default HMR port 24678, shared by every instance. |
| 2026-11-10 | Explicit name check: with the probe project `devslot-probe`, a volume or network whose resolved name starts with `devslot-probe` follows the project (implicit name or `${COMPOSE_PROJECT_NAME}-data`) and is accepted. Any other name, and `external: true`, is an error. | The merged config gives every volume and network a `name`; only names that do not follow the project are shared between instances. |
| 2026-11-10 | A variable found by several sources gives one entry: the first source in the spec order (`PORT`, `[ports] extra`, `VITE_HMR_PORT`, compose) wins, and the compose service and container port are kept when the compose also publishes it. | The registry stores ports by variable name. |
| 2026-11-10 | Reserved variables never get a sentinel and are not managed: `PATH`, `HOME`, `PWD`, `SHELL`, `USER`, `TMPDIR`, and every name starting with `LD_`, `DOCKER_`, `COMPOSE_`, `BUILDX_` or `XDG_`. In the probe environment, the passed variables are applied after the sentinels. | Security review: `${HOME}` without a default became `HOME=61000`, a relative path, and Docker then loaded a CLI plugin shipped inside the repo (code execution during a read-only `ds doctor`). |
| 2026-11-10 | Output never relays Compose stderr, and findings never print a resolved string from the compose model: only keys (service, volume or network key, variable names), port numbers and bind mount source paths. A rejected file gets a fixed message with the hint `run docker compose -f <file> config --quiet to see why`, the file name shell-quoted. | Compose loads the `.env` of an `include:`d file's project directory despite `--env-file /dev/null`, so the probe can see `.env` values, and its parse errors quote them. The cleared environment protects the main file only. |
| 2026-11-10 | `.env`, `.env.example` and `.env.test` are read only when they are regular files of at most 1 MiB; otherwise `ds doctor` reports an `env_unreadable` error. The same limit on `devslot.toml` and `devslot.local.toml` is a tool failure (exit 2). Docker probes run in their own process group, killed as a whole on timeout. | A FIFO `.env` hung the tool forever, a symlink to `/dev/zero` exhausted memory, and a timed out probe left the compose plugin running. |
| 2026-11-10 | `ds doctor` in a folder with neither a compose file nor a `.env` (and nothing to create `.env` from) keeps reporting the `.env` missing error, exit 1. | Confirmed by the user: the spec's check applies whatever the compose situation. |
| 2026-11-10 | Instance name: `<repo>-<folder>-<hash>`, where the folder loses the repo name as a prefix (`~/dev/my-links` gives `my-links-3f2a`, `~/dev/my-links.feat-auth` gives `my-links-feat-auth-3f2a`). The hash is the first 4 hex characters of the SHA-256 of the canonical path, lengthened (6, 8...) when the name is already used by another path. The name is stored at registration and never recomputed. | Matches the spec example, avoids `my-links-my-links-...`; a shared name would mean a shared compose project and shared volumes. |
| 2026-11-10 | `ds run` runs the same checks as `ds up` on the dev compose: an error blocks the command, warnings are shown. | `ds run -- just dev` usually starts the compose through the recipe. |
| 2026-11-10 | Registry format: each `[[instance]]` stores `path`, `name`, `slot`, `range = [first, last]` (the ports the slot covered when it was assigned), `ports` (variable to port), and `details` (variable to `{ kind = "web" or "service", service, target }`, the kind stored as discovery found it). A top-level `opted_out` list of paths is accepted. Entries with overlapping ranges, shared ports, duplicate paths or names, or a port outside the instance's range make the registry malformed: ds refuses to rewrite it. | `ds ls --json` and `ds info` must not call Docker for every instance; `PORT` stays `web` when a compose also publishes it, as in `ds doctor`. |
| 2026-11-10 | Global config: `[slots] first_port = 20000`, `last_port = 29999`, `size = 50` (max 100). A known instance keeps its stored range after a size or range change; a new slot is taken only when its range overlaps no registered range and holds no registered port. `ds doctor` warns when the current instance's range no longer matches the slot geometry. A migration command is parked as an idea. | Changing the size must not move or overlap existing instances; migrating changes an instance's ports and needs its own design. |
| 2026-11-10 | `[env]` keys must match `[A-Za-z_][A-Za-z0-9_]*` and values must not contain NUL. Reserved names (the reserved variable list, `COMPOSE_*` included, plus `DEVSLOT_*`) are refused in both files. Only `devslot.local.toml` may force a managed port variable (example: `PORT = 3333` for an OAuth callback registered on that port); in `devslot.toml` it is an error. `${NAME}` in a value is replaced by an instance variable; an unknown name is an error. | A committed `devslot.toml` could inject shell code through `eval "$(ds env)"` or break isolation with `COMPOSE_PROJECT_NAME`; the local file follows the spec's "force a value through devslot.local.toml". |
| 2026-11-10 | `ds info` shows name, path, slot, range and ports; the services state comes with `ds up`. Unregistered checkout: `ds info` says so and suggests `ds up` (exit 0, JSON `registered: false`); `ds env` fails with exit 1. The first registration of a checkout announces its compose project name and that containers and volumes created before devslot stay under their old project name. | The main checkout loses access to its pre-devslot database volume; keeping `app-dev` is impossible since the template and my-links both use it. |
| 2026-11-10 | `ds run` overriding warnings print old and new values only for port variables, `COMPOSE_PROJECT_NAME`, `COMPOSE_FILE` and `DEVSLOT_*`; other keys are named without values. Exec failures: not found 127, not executable or no interpreter 126. | The caller's value of an `[env]` key can hold a credential. |
| 2026-11-10 | The committed `devslot.toml` `[env]` may only set keys already present in `.env` (block stripped) or `.env.example`; any other key is an error that blocks `ds run`. A denylist of names that make ordinary programs run code (`GIT_*`, `SSH_*`, `BASH_ENV`, `ENV`, `PROMPT_COMMAND`, `PS0`-`PS4`, `IFS`, `NODE_OPTIONS`, `PYTHON*`, `PERL5*`, `RUBY*`, Java options, `EDITOR`, `PAGER`...) is refused in both files. `[ports] extra` and `ignore` names follow the same name rules as `[env]`. A tracked `devslot.local.toml`, or a forced port that falls on another instance, is an error. `[env]` values take part in the compose probe, so the checks see what `ds run` will inject. `[env]` accepts strings and integers. `ds run` warnings show a caller value only when it is a port number or a devslot variable. | Security review: quoting stops shell syntax, not variables read as code (`GIT_CONFIG_*` with `core.fsmonitor` ran a command at every git call after one `eval "$(ds env)"`). A denylist alone is never complete; the spec's use of `[env]` is rebuilding app values that `.env` already declares. |
| 2026-11-10 | `ds env` (sh and json) prints only the port variables, `COMPOSE_PROJECT_NAME`, `COMPOSE_FILE`, `DEVSLOT_*` and the `[env]` values of `devslot.local.toml`; the `[env]` values of the committed `devslot.toml` go only to `ds run` (and to the `.env` block in phase 3). The denylist is extended (zsh prompts, build tools, package manager prefixes) and matched without case. `ds run` warnings never show the caller's old value except for `COMPOSE_*` and `DEVSLOT_*` variables. This supersedes the "declared in .env" row as the security barrier; that rule stays as a scope rule. | Re-review: a hostile repo also commits `.env.example`, so declaring a key there let `PROMPT`, `RUSTC_WRAPPER` or `CC` reach the user's shell through `eval "$(ds env)"` and run code. `ds run -- just dev` already runs the repo's own scripts, so committed values add nothing there; the persistent shell is the real target. |
| 2026-11-10 | A managed port variable's name must end in `PORT` (case-insensitive), whether it comes from the compose file or from `[ports] extra` of the committed `devslot.toml`. A compose variable that drives a published port under another name is not managed and gives a warning suggesting a `_PORT` name; a committed `extra` name without the suffix is a config error. `devslot.local.toml` is not restricted. | Re-review: a repo-chosen name such as `PSQLRC`, `KUBECONFIG` or `AWS_CONFIG_FILE` was exported by `ds env` with a number that the tool reads as a relative config file path, letting a committed file run code; no denylist can cover every `*RC`, `*_FILE` or `*CONFIG*` name. |
| 2026-11-10 | `ds doctor` exits 2 when the registry or the global config is malformed. A port forced in `devslot.local.toml` is used as written, without `${NAME}` substitution. `ds run` prints its warnings and registration notices on stderr. | Validated by the user after phase 2: a broken machine state is a tool failure, a forced port is a literal number, and stdout stays the command's own. |
| 2026-11-15 | Phase 3 small choices (user trusted the recommendations): `COMPOSE_FILE` in the block holds paths relative to the checkout root, the dev compose then the existing `compose.override.*`, joined by `:`; a configured compose name containing `:` is an error. `ds up` runs `docker compose up -d --wait --wait-timeout 120`. `ds reset` deletes the data then starts the services again, without confirmation. `ds reset <service>` stops and removes that service's container and anonymous volumes (`rm -s -f -v`) and its named volumes found by the labels `com.docker.compose.project` and `com.docker.compose.volume`, refuses when another service mounts the same named volume, warns that bind mount sources are not reset, then starts the service again. Before `up`, a service port busy and not published by the instance's own containers (`ps -a` of its project) is an error; web ports are checked only when `run` is set; no program name in v1. | Agents chain a migration right after `ds up` or `ds reset`, and a relative `COMPOSE_FILE` survives `git worktree move`. |
| 2026-11-15 | `ds rm` keeps a `.env` that ds created and removes only the block. `ds rm` on an unregistered checkout removes a block if present and records the opt-out, with no Docker call; Docker deletions always take the project name from the registry entry of the canonical path, never from a `.env` block. `ds rm` checks everything that does not need Docker first (`.env` regular, block well-formed, registry readable, lock obtained); a failure after `down -v` says the data is already deleted, and running `ds rm` again finishes the job. Block removal ignores `[write] enabled` and the ignore check. Block removal, instance removal and opt-out happen in one lock hold and one registry save. | A created `.env` cannot be told apart from one the user has since edited; a block anyone can write must not choose what gets deleted; deleting data and then failing on a file must not leave a half state. |
| 2026-11-15 | `ds rm` and `ds prune` ask for confirmation only when stdin and stderr are terminals (never `/dev/tty`); without a terminal and without `--yes` they change nothing and exit 1. `ds prune` forgets an instance whose folder is gone (`NotFound` only) only after its `docker compose -p <name> down -v --remove-orphans` succeeded, run from the state directory with inherited `COMPOSE_*` variables removed; it also forgets opted-out paths whose folder is gone. Superseded by the 2026-11-15 row on deleting an instance's data by label (the `down -v` cleanup of `ds prune`). | An agent must never hang on a prompt; an entry forgotten before cleanup leaves volumes no command lists again; Compose loads the compose file and `COMPOSE_FILE` of the cwd even with `-p`. |
| 2026-11-15 | The "output never relays Compose stderr" rule covers probes and findings only. The commands that act on the instance (`up`, `down`, `reset`, `rm`, `prune`) show Compose's own output. They run with the caller's environment minus inherited `COMPOSE_*`, plus the instance environment. | Their output is the user's own stack, as with a manual `docker compose up`, and `up` cannot be debugged without it. |
| 2026-11-15 | The `run` key runs through `/bin/sh -c`, replacing ds (exec), and is printed on stderr first. | The value is already code chosen by the repository; splitting it into words adds no safety. |
| 2026-11-15 | `[write] enabled = false` (global `config.toml` or `devslot.toml`, local file wins): ds neither creates `.env` nor writes the block, and warns when a block already exists. A `.env` without a final newline gets one before the block, so `ds rm` leaves that one extra newline; every other file comes back byte for byte. A block value is written bare when made of `[A-Za-z0-9_./:@,+=%-]`, single-quoted when it holds no `'`, `$`, `\` or newline, refused otherwise (the error names the key, never the value). | Dotenv parsers disagree on escapes and interpolation; refusing is safer than guessing. |
| 2026-11-15 | `.env` is created under the registry lock, after the checks pass, from the main checkout's `.env` (block stripped) or `.env.example`; permissions copied from the source. Every `.env` write goes through a temp file with a unique name (`.env.devslot-<pid>-<random>`) in the checkout root, after removing stale temps of that pattern, then `rename`; a `.env` that is a symlink or not a regular file is refused. All block writes happen under the registry lock, and `ds ensure` re-reads the registry, the opt-out list and `.env` under the lock before writing. | Parallel hooks on one checkout must give one block; a killed write must not block later ones or leave a copy of secrets to commit. |
| 2026-11-15 | `ds ensure` is a no-op outside git, outside the `[auto]` scope (checked before running git), for an opted-out checkout and without a dev compose file on disk. A refused registration is cached in the state directory, keyed by checkout path and a fingerprint (size and mtime of the compose files, overrides, `.env`, `.env.example`, `devslot.toml`, `devslot.local.toml`, `.gitignore`): while the fingerprint is unchanged, ensure exits 0 silently. Exit codes: 0 done or no-op, 1 refused, 2 tool failure. `run_git` passes `-c core.fsmonitor=false`. | The hook runs before every agent command: a refusal must be reported once, not hundreds of times, and must not cost a Docker probe each time. |
| 2026-11-15 | DevSlot manages worktrees. The plugin's `WorktreeCreate` hook calls `ds hook worktree-create`: `git worktree add` in `<[worktrees] root>/<repo>/<name>` (default `~/dev/.worktrees`), on branch `<name>` (reused when it exists, else created from the branch checked out in the main worktree), then registers the checkout (slot, `.env`, block, no service started) and prints the path last on stdout; a refused registration warns but still creates the worktree. `WorktreeRemove` calls `ds hook worktree-remove`: deletes the instance's containers and volumes and forgets it (kept in the registry for `ds prune` when Docker fails), `git worktree remove --force`, then deletes the branch only when merged into the main worktree's branch. The `PreToolUse` hook (`ds ensure`) stays as a safety net. This supersedes the spec's "DevSlot only registers through `ds ensure`". Superseded by the 2026-11-15 row on `ds hook worktree-create` and `worktree-remove` (the git worktree is removed before any data is deleted). | User's workflow: every Claude Code session works in its own worktree outside the repo, created and removed by these hooks; a `WorktreeCreate` hook replaces Claude Code's git logic entirely, so a single tool must own creation, and the slot lives exactly as long as the worktree. |
| 2026-11-15 | The block also holds `DEVSLOT_INSTANCE` and `DEVSLOT_SLOT`; `ds info --json` and `ds ls --json` give each web port a `url` (`http://localhost:<port>`). | A backend or a dev mobile app (one app id for every instance) can show which instance it talks to, the project deciding how. |
| 2026-11-15 | Deleting an instance's data (`ds rm`, `ds reset` without service, `ds prune`, the worktree-remove hook) never goes through a compose model: containers, volumes and networks are listed by the label `com.docker.compose.project=<name from the registry entry>` and removed by id or name (`docker rm -f`, `docker volume rm`, `docker network rm`). `compose down -v` is no longer used. | Security review: Compose resolves a volume `name:` with the checkout's `.env`, and without `-f` searches parent folders for a compose file even with `-p`; a committed `.env.example` with `VOL=victim_pgdata`, or a `~/compose.yaml`, made `down -v` delete another project's volume. |
| 2026-11-15 | Before `up` (and the restart of `ds reset`), the isolation checks also run on the model resolved exactly as `up` resolves it (`config --format json` with the checkout's `.env` and the instance environment, output kept in memory, never printed): `container_name`, `external: true`, or a volume or network name not starting with `<instance name>_` or `<instance name>-` blocks with exit 1, the message naming keys only. `.env` and its creation source are read through a handle opened without following symlinks; a symlinked creation source is refused. | The probe resolves with a cleared environment, so a name built from a `.env` value escaped the registration checks; a committed `.env.example` symlinked to `~/.aws/credentials` was copied into the checkout. |
| 2026-11-15 | `ds ensure` probes Docker with a 5 s timeout and a per-checkout single-flight lock (a parallel hook on the same unregistered checkout exits 0 at once); `NoRoom` and forced-port-conflict refusals are cached 5 minutes; git calls have a 10 s timeout. | Perf review: a hung Docker stalled every hook 30 s, each parallel call paying it again. |
| 2026-11-15 | Creation source of `.env`: the main checkout's `.env` may be a symlink (followed, target must be a regular file of at most 1 MiB); a symlinked `.env.example` is refused. `ds doctor`, registration and `ds ensure` use the same predicate. Container removal uses `docker rm -f -v`, so anonymous volumes of the instance's containers go too. | The main `.env` is the user's own untracked file, often managed by dotfiles; `.env.example` is committed by the repository and could point at any file of the user. An image `VOLUME` (postgres) left the database files behind. |
| 2026-11-15 | `ds hook worktree-create` registers the new worktree only when it is inside `[auto]` and has a dev compose file (as `ds ensure`), and lets git run the repository's `post-checkout` hook, as Claude Code's own worktree creation does. `ds hook worktree-remove` acts only on the root of a linked worktree (never the main checkout or a subfolder), removes the git worktree before deleting any data (a locked worktree keeps its data and entry), and deletes the branch only when it is named like the worktree folder and `git merge-base --is-ancestor` confirms it is merged into the main checkout's HEAD. `ds hook pre-tool-use` always exits 0 and denies obvious `ds rm` / `ds prune` forms (a guard rail, not a sandbox: quoting, wrappers and `ds run --` are handled, arbitrary shell tricks are not). | 2026-11-21 | `ds ensure` refreshes the registration of a registered checkout when the inputs of port discovery changed since its last registration, not only when `[env]` refers to an unknown variable. The discovery fingerprint is the size and modification time of the selected dev compose file, its existing overrides, `devslot.toml`, `devslot.local.toml` and `.env.example`, each line carrying the file name; `.env` (rewritten by every block write) and `.gitignore` are left out. Every successful registration (`ds run`, `ds up`, `ds ensure`, worktree creation, any change kind) writes it to `<state>/ensure/<key>.discovered`, atomically and best effort, taken before the registration so a file edited during the probe triggers another refresh. A missing or different stamp makes `ds ensure` refresh once, as an extra step before the block repair, under the refusal cache and the single flight. A refresh that changes nothing in `.env` is silent, the standing warnings included. A refresh that is silenced, busy, refused, failed on Docker or out of budget does not stop the call: the block is still repaired from the registry, then the outcome is reported (a refusal once, with a closing line that says the registration was not refreshed, and its cache entry is re-saved against the new `.env` so the next call is silent). `ds rm`, `ds prune` and worktree removal delete the stamp; the stamp is also deleted 30 days after its last write, like the other files of the checkout, so a checkout not registered again for 30 days pays one probe.
